## 2026-08-13：第 4 章第 21 节《按合约设计》

### 用户理解

- 合约用于明确程序的输入和输出边界，保证程序正确并限定合理使用范围。
- 合约包含输入条件和输出条件。
- 用户将继承理解为：子类应包含父类输入和输出边界的全部。
- 当前疑问：类不变项。

### Codex 判断

- 正确抓住了前置条件、后置条件和边界约束的核心作用。
- 需要补充：合约通常还包括类不变项；它描述对象在可观察操作前后都必须保持的稳定性质。
- 继承表述需要更精确：子类应遵守父类对外合约，不能要求调用者提供更强的前置条件，也不能承诺更弱的后置条件；同时必须保持父类不变项。

### 针对性解释：类不变项

类不变项是“只要对象处于可被外部使用的稳定状态，就必须成立”的条件。构造完成后成立；每个公开方法执行前后也应成立。方法内部可以暂时破坏它，但返回给外部前必须恢复。

例如，一个表示银行账户的 Python 类可能规定余额不能为负数：

```python
class Account:
    def __init__(self, balance=0):
        assert balance >= 0
        self.balance = balance

    def withdraw(self, amount):
        assert 0 <= amount <= self.balance
        self.balance -= amount
        assert self.balance >= 0  # 类不变项
```

这里“余额始终不小于 0”不是某一次调用的输入条件，而是这个对象在整个生命周期中必须保持的性质。它帮助调用者建立稳定预期，也让错误更早暴露。

### 补充知识：继承与合约

若父类方法允许 `withdraw(10)` 在余额足够时成功，子类不能无故增加“必须是工作日”之类更强的前置条件；否则原本适用于父类的代码替换成子类后可能失效。子类可以给出更强的结果保证，但不能削弱父类的后置条件或不变项。

### 理解检查结果

用户判断：如果 `User` 的不变项是“用户名不能为空字符串”，而 `AdminUser` 允许将用户名改为空字符串，则违反父类合约，因为子类允许对象进入违反父类不变项的状态。

评价：判断正确，类不变项达到基本掌握；后续继续验证前置条件和后置条件的继承关系。

## 2026-08-13：第 4 章第 22 节《死程序不说谎》

### 用户理解

- 遇到异常应尽快抛出，而不是让异常状态留到后面。
- 在异常仍存在时继续运行，通常不如尽早停止更合理。
- Python 项目中，传入变量不符合预期时，应尽早检查并使用 `raise` 报错，避免错误变量继续传递。

### Codex 判断

- 已正确理解“尽早失败”和“避免错误状态扩散”。
- 需要补充边界：尽早失败不等于所有异常都必须让整个程序退出；可以在明确边界处捕获、记录、转换或恢复，但不能静默吞掉错误，或让程序继续产生不可信结果。

### 理解检查结果

用户判断：Web 服务发现非法请求参数后返回 HTTP 400 并记录日志，符合“死程序不说谎”，因为程序明确提醒了异常并给出处理结果，而不是默许异常继续传播。

评价：判断正确，已理解“合理捕获/转换异常”和“掩盖错误”的区别。概念状态提升为基本掌握。

## 2026-08-13：第 4 章第 23 节《断言式编程》

### 用户理解

- 断言式编程用于用代码检查原本认为必须成立的情况。
- 断言会在断言处停止；普通错误处理还可能记录日志、关闭系统资源等。
- Python 项目中常在单元测试中使用 `assert`。
- `assert` 不能替代输入校验；断言与输入输出检查及错误处理不是同一个概念。

### Codex 判断

- 正确理解了 `assert` 不应替代外部输入校验。
- 需要修正：断言不是证明程序不会报错，而是将程序员对内部条件、不变量或不可达状态的假设写成可执行检查。
- 断言不只用于单元测试，也可用于检查内部不变量、函数内部前置条件和理论上不可达的分支。
- 外部输入不满足要求时，应使用显式校验和适当的错误响应；Python 的 `assert` 可能在优化运行模式下被移除，因此不能承担正式输入校验职责。

### 理解检查结果

用户判断：第二个场景不适合 `assert`，应使用显式异常；对第一个场景，用户认为 `b != 0` 适合用 `assert` 检查。

评价：第二个判断正确。第一个判断需要修正：`divide(a, b)` 的 `b` 通常是调用者提供的输入，因此 `b != 0` 属于输入前置条件，不应仅依赖 `assert`。关键区分不是条件是否可能变化，而是条件来自外部输入还是程序内部必须成立的假设。若调用者传入 0，可显式抛出 `ValueError`，或让 Python 的 `ZeroDivisionError` 表达错误；若某个更高层内部逻辑已经保证 `b != 0`，在内部边界使用断言检查这个保证才更合适。

## 2026-08-13：第 4 章第 24 节《何时使用异常》

### 用户理解

- 本节要解决的问题是：什么时候使用异常，以及如何使用异常。
- 用户认为：如果去除所有异常处理器，代码依旧无法正常运行，说明还存在未被处理的异常。
- 用户判断：用户指定文件不存在应抛出异常；不理解 `/etc/passwd` 有什么特殊之处。

### Codex 判断

- 主题把握正确：本节核心是“异常留给意外事件”，并介绍错误处理器作为另一种选择。
- 第 2 点需要修正：原书检验法是“如果移走所有异常处理器，这些代码是否仍能运行？如果答案是‘否’，说明异常正被用在非异常的情形中”，而不是“还存在未被处理的异常”。
- 文件场景判断反了：`/etc/passwd` 在 UNIX 系统上应当存在，缺失属于意外，抛出 `FileNotFoundException` 合理；用户指定文件可能不存在，属于可预期情形，应检查存在性并返回错误。

### 原书依据（第 24 节，印刷页 100–102）

- 异常很少应作为程序正常流程的一部分使用；异常应留给意外事件。
- 检验法：如果移走所有异常处理器，代码是否仍然能运行？答案是否，说明异常正被用于非异常的情形。
- 文件应当存在而缺失 → 异常；不确定是否应当存在 → 错误返回。
- 错误处理器是检测到错误时调用的例程；可作为异常的替代或补充（如 C 语言、Java RMI 场景）。

### 理解检查结果

用户回答：用户指定文件不存在应抛出异常；不理解 `/etc/passwd` 的特殊之处。

评价：判断反了，概念暂记为初步理解；需要巩固“应该存在/可能不存在”的区分。待完成后续小场景验证。

### 理解检查结果（第 2 轮）

用户回答：`config.yaml` 缺失应抛出异常，用户选择的 CSV 缺失应返回错误。

评价：判断正确，已掌握“文件应该存在/可能不存在”的区分。用户进一步询问返回错误与抛出异常的区别。

### 针对性解释：返回错误与抛出异常的区别

原书角度：返回错误是局部的，被调用例程把错误状态交回调用者，由调用者决定下一步；异常是非局部控制转移，出错后沿调用栈向上寻找处理器，相当于级联的 goto，正常流程与错误处理被分开，但例程和调用者的耦合也更强。

补充知识（Python 机制）：`raise` 只中断当前函数并把异常沿调用链传播，不一定导致整个程序中断；只有异常一路传播到最顶层仍无人捕获时，程序才会终止并打印 traceback。返回错误时函数正常返回（例如返回 `None`、`False` 或错误对象），调用者可以选择检查并处理，也可能忘记检查而让错误状态继续传播。

工程选择：预期会发生、调用者有能力处理 → 返回错误；不该发生、调用者通常无法处理或处理动作固定 → 抛异常。这是原则而非语言硬性规定。

### 理解检查结果（第 3 轮）

用户回答：调用者忘检查返回的错误值，后续程序会带着错误运行；异常没人捕获，会在异常抛出处中断程序。

评价：第一半正确。第二半需要精确化：未捕获异常不是停在抛出点，而是从抛出点沿调用栈向上传播，沿途执行 `finally`/`with` 清理；只有到达顶层仍无人捕获，整个程序才终止，traceback 指向抛出点。

## 2026-08-14：第 4 章第 25 节《怎样配平资源》

### 用户理解

- 本节解决的问题是资源配平，即分配资源和回收资源要平衡。
- 重要概念：分配资源要有始有终，分配了资源就要同步考虑回收。
- 疑问：Python 是否存在自动回收资源的机制。

### Codex 判断

- 主题和核心提示把握正确：原书提示 “Finish What You Start（要始终如一/有始有终）”，即分配资源的例程或对象应负责释放资源。
- 原书还扩展了：嵌套资源按分配次序的相反次序释放；多处分配同一组资源时保持相同次序；类把资源封装起来，构造器/析构器对称；动态数据结构要设定语义不变项；用包装和工具检查资源配平。

### 补充知识：Python 的资源回收

- Python 有自动内存回收（引用计数 + 分代垃圾回收），但回收时机不保证；依赖 `__del__` 清理文件、连接、锁等有限资源不可靠。
- 可靠做法是 `with` 语句（上下文管理器）和 `try/finally`；`with open(path) as f` 保证异常时也执行清理。

### 理解检查结果

用户回答：写法 A 中途抛异常时 `f.close()` 不保证执行；写法 B 通过 `with` 上下文管理器保证文件关闭，符合“有始有终”。

评价：判断正确，概念记为基本掌握；后续在数据库连接、锁等资源场景中继续验证。

## 2026-08-17：第 5 章第 26 节《解耦与得墨忒耳法则》

### 用户理解

- 本节解决的问题是减少代码间的耦合。
- 重要概念：得墨忒耳法则，减少跨对象间的调用，保持低耦合。
- 疑问：如何评价一个 Python class 是否过度包装。

### Codex 判断

- 方向正确；需更精确：得墨忒耳法则规定方法只能调用自身、方法参数、自己创建的对象、直接持有的组件对象的方法，不能为了调用第三个对象而穿过某个对象。
- 链式调用如 `aSelection.getRecorder().getLocation().getTimeZone()` 同时耦合多个类；应让当前对象直接提供所需结果。
- 遵守法则的代价是大量转发包装方法，有运行时和空间开销，需要在解耦与性能之间权衡。

### 补充知识：Python 中过度包装的判断

- 包装方法只是原样转发、没有语义/校验/转换，接口规模明显大于实际服务、调用者看不出类负责什么、热路径上有可测量的性能开销时，可能过度包装。
- 若包装吸收内部结构变化、保护不变项、隐藏细节，则是有价值的封装。

### 理解检查结果

用户回答：链式调用不符合法则，应在 getOrder/getPayment 内部设置分发函数作为返回。

评价：思路正确，表述需精确：应让调用者已经持有的对象直接提供结果，例如增加 `customer.getOrderAmount()`，内部再委托 order/payment 完成，而不是让调用者沿链自己取。概念记为基本掌握。

### 用户理解

- 本节讨论元数据的重要性。
- 重要概念：元数据是数据的数据，也是对应用进行描述的数据。
- 疑问：Python 中配置元数据是否要以文件形式存储；如何防止元数据被滥用。

### Codex 判断

- 方向正确；更精确：核心是把容易变化的细节赶出代码，让应用由元数据配置和驱动。原书提示为“要配置，不要集成”和“把抽象放进代码，细节放进元数据”。
- 元数据的定义理解正确。

### 补充知识：Python 配置与元数据防滥用

- 纯文本是常见做法，但文件并非唯一方式；TOML/YAML/JSON/INI/环境变量均可承载配置。密钥建议走环境变量或密钥管理服务。
- 长期运行的服务器进程可支持运行中重载配置；小型 GUI 程序启动时读取即可。
- 元数据应保持为数据而非代码：要有 schema 与校验、纳入版本管理、不对配置内容 `eval`、把配置当作外部输入对待、为关键配置组合补测试。

### 理解检查结果

- 第 1 轮：用户认为折扣逻辑应放入元数据；已修正为机制留代码、数值留元数据。
- 第 2 轮：用户能区分阈值/额度进元数据、满减动作留代码；判断正确，概念记为基本掌握。

## 2026-08-17：第 5 章第 28 节《时间耦合》

### 用户理解

- 本节解决代码的时间耦合问题。
- 重要概念：用并发方法设计和思考，让接口更整洁、耦合更低。
- 疑问：并发过程中确实存在线性流程时如何处理或规避。

### Codex 判断

- 方向正确；时间耦合包含并发和次序两个维度，原书提示是“分析工作流以改善并发”和“用服务进行设计”。
- 对象在任何被调用时刻都须有效，隐藏调用次序本身就是时间耦合。

### 补充知识：真实线性依赖的处理

- 用工作流分析区分真实依赖与顺手写成的顺序。
- 把依赖显式化：B 需要 A 的结果就把结果作为 B 的输入，而不是依赖 A 恰好已执行。
- 并发中用 Future/Promise、队列、事件、同步屏障等表达等待；Python 对应 `asyncio`、`concurrent.futures`、`threading.Event` 等。
- 隐藏状态的两个调用步骤往往是设计问题，应让接口返回自带状态的对象。

### 理解检查结果

用户回答：`b(a())` 把 A 的结果作为 B 的输入，依赖显式化，时间耦合更低；先 `a()` 再 `b()` 依赖 A 恰好运行完成，时间耦合更高。

评价：判断正确，概念记为基本掌握。
